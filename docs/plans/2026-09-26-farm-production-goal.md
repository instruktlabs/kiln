## Sequence and concurrency

1. **Prepare the actual authoring workspace.** Use the qualified packaged candidate in a separate workspace, the existing setup skill, and normal CLI/MCP entrypoints. Record its exact identity, profile/material revisions, inventory and reference archive. Keep engine implementation and historical example assets outside authors' context. Confirm actual GPU captures and durable run-log collection before the first useful production run.
2. **Establish direction together.** Review the existing individual references, a shared scale lineup and material samples. Resolve the farmer/door/tractor/barn/gate relationship before detailed modeling. Set the initial shape, palette and material language, then run the small model slice. Include an early coarse farmer rig and walk probe as well as the cow; hard-surface success alone does not qualify creatures and characters.
3. **Approve a coherent set of anchors.** Bring the selected tractor and cow together with a meaningful building section, fence/gate joint, barrel or bale, cabbage and tree from the existing brief's material/shape slice. The farmer probe supplies the human scale and articulation check. Review the set together before broad production. These can be partial assets at this milestone, with unfinished work labeled.
4. **Produce in bounded parallel groups.** Start with at most three active authors plus the coordinating lead. Schedule related families into those slots: buildings/mills; tractor/trailer; fence modules and props; farmer/livestock; crops/vegetation. Keep coupled assets with one family owner, reuse accepted conventions and integrate every completed batch into the proving scene. Family owners can rotate as slots become free; these are not five simultaneous workers.
5. **Review and mine traces between batches.** Resolve shared drift, import/animation defects and repeated tool failures before multiplying them. The coordinator publishes any new shared profile/material revision and identifies which saved assets need reconsideration. Integrate retained exact revisions instead of rebuilding an unspecified latest state.
6. **Qualify the complete scene and delivery.** Finish the 23 assets and all promised motion, measure the real proving scene under controlled conditions, resolve material issues, and validate editable/runtime delivery and owner acceptance.

Each author owns distinct source files and asset IDs. The lead is the single writer for shared design decisions, material dependency revisions and the integrated scene. Workers propose changes and can continue independent work against their pinned revision. This avoids one author's palette change silently invalidating another author's review.

Parallel authoring does not imply parallel native GPU execution. Use the shared local renderer and its admission/queue behavior; reduce author concurrency if queue delay or memory pressure starts harming iteration. Do not start a renderer per agent or invent retry/fallback routes. Performance qualification runs with production workers and competing intensive jobs paused. Live Review remains observation: feedback goes through the current agent conversation.

## Coherent direction that can evolve

The shared design profile should specify more than colors: proportions, silhouette density, faceting and normal treatment, edge thickness, detail visible at gameplay distance, material roughness and texture repeat scale, degree of wear, and animation exaggeration. The existing Farm direction is friendly faceted game art with restrained matte materials. Imported photographic PBRs are optional; a procedural texture earns inclusion through visible benefit and coherent scale.

Every assignment receives a self-contained written brief covering its role in the scene, desired character and shape language, dimensions and attachment/pivot conventions, relevant palette/material pins, intended viewing distances, motion/function requirements, delivery constraints and visible completion criteria. Identify actual requirements separately from suggested details and state the room for creative interpretation. Supply individual concept images and accepted anchor views when useful to the chosen workflow; image copying is not a quality gate. The owner's preference for text-led Opus authoring informs future prompt design but is not a demonstrated universal model advantage. Archive exact prompts, context choices and supplied images separately: current project exports retain their references, not the concept-image bytes themselves.

Use the same render setup for comparisons. Review silhouette and contact first, then construction and functional parts, then materials and motion. Place assets beside accepted anchors and their actual neighbors; an attractive isolated object can still fail the pack. Record clear visual reasons for acceptance or revision. Owner review sets the artistic bar at the anchor milestone and complete pack; return earlier when a meaningful change would alter the agreed direction.

Agents can improve the profile. Each shared change should include a reason, before/after views, affected assets and an explicit revision. Test it on representative assets before propagating it. Revalidate affected saved outputs; a new material lock does not rewrite old assets. Intentional exceptions should be named and visible, rather than becoming accidental style drift.

## Trace mining as part of production

Collect exportable prompts, tool calls/results, user-visible feedback, source changes, captures and outcomes. Hidden model reasoning is neither required nor a portable data source. Use native harness records plus a small run manifest; do not make a new universal orchestration/proxy system a prerequisite for this pack.

The existing [tier-two driver](../../scripts/tier2-dogfood.mjs) supplies useful examples of Codex JSON, Claude/AGY streaming JSON and run evidence capture. Its blind-onboarding evaluation workflow is not a production scheduler. The [lightweight MCP observer](../../scripts/observe-mcp.mjs) omits full source/result bodies, while the [shipping evaluator observer](../../scripts/evaluation/observe-shipping.mjs) applies budgets and deadlines. Verify trace completeness on the actual selected authoring route before reusing either; neither is a ready-made neutral Farm recorder. Record requested model/effort separately from any identity/settings confirmed in harness events.

For each run retain:

- Run/asset IDs, parent revision, requested model/effort, harness-confirmed identity/settings when available (otherwise unknown), harness version and interface used.
- Exact package/tool/skill versions, project revision, material dependency identities, reference and brief versions.
- Initial source and meaningful revisions, actual tool requests/results and errors, exact GLBs, GPU captures/fidelity and saved artifact IDs.
- Reviews and their author, rejection reasons, corrective actions, final disposition and remaining limitations.
- Elapsed time, render/queue timing and token/cost data when available, with missing observations labeled unavailable.

Retain rejected candidates and useful intermediate successes, not just final exports. Live Review's default 200-operation/256-MiB journal is disposable observation storage, not a complete campaign archive. Capture harness logs from the start and preserve meaningful artifacts before eviction. Saved assets identify selected revisions; retain exact dependency manifests and editable exports for portable resource closure. The run manifest maps each authoring run to its saved asset revision because Save Reviewed does not itself assign model/harness authorship. A separate run archive preserves the wider history. Pinning everything is not a retention strategy. Raw logs stay private; any shared trace extracts should exclude credentials and unrelated conversation content.

After each batch, inspect both repeated failures and efficient successes. Useful categories are ambiguous art direction, missing skill guidance, tool/engine defects, harness/image-delivery problems, material/UV mistakes, geometry or rigging mistakes, excessive/no-op iterations, and inadequate visual review. Track time to first acceptable revision and successful correction patterns as well as raw error counts. Attribution should name the exact tool or source revision and the evidence, not simply blame the model.

Turn a recurring finding into a small reproducible case. Fix shared engine defects in the engine repository, clarify shared skills when instructions were missing, and retain pack-specific creative choices in the project. Observe failing behavior before a behavior fix and rerun the affected acceptance checks. Change package/skill versions between batches, recording the boundary; do not silently change the system in the middle of a comparison. Carry successful workflows into guidance without imposing Farm's art rules or project membership on standalone authors.

## Optimization and completion

Optimize for the actual scene and intended views while preserving the agreed look. Start with material and geometry reuse, useful detail density, correct UV/repeat scale, clean pivots and affordable animation. Measure draws, texture residency estimates, overdraw, load time and frame pacing alongside triangle counts. A low triangle count alone does not make a useful asset. Consider instancing, atlases, LODs or compressed derivatives where measured benefit justifies their added workflow and consumer requirements.

The numerical targets in the Farm brief are provisional. Qualify them on the actual scene at a stated browser drawing-buffer size and hardware profile, including cold loading, steady navigation and simultaneous animation. Earlier small dashboard measurements do not establish full-screen Farm performance. Record the browser/renderer, resource and artifact identities, concurrent load and measurement limits. CPU structural QA and GPU appearance review serve different purposes; degraded CPU images cannot qualify materials.

The goal is complete when:

1. All 23 inventory entries have exact saved revisions, completed hidden sides and functional parts, coherent materials/scale and the promised clips or state swaps.
2. The proving scene includes every unique asset and meaningful repeated instances, demonstrates their interactions, and meets an explicitly adopted measured performance profile.
3. Owner review accepts the art direction and finished pack, with any remaining limitations recorded. Automated checks and model reviews support that decision.
4. Editable and runtime bundles are distinct. A clean workspace can rebuild from the editable sources, exact maps/recipes and recorded settings using the recorded qualified runtime/dependency environment offline; compare saved and rebuilt hashes. The editable ZIP does not embed the engine. Runtime GLBs load and play their promised motion in Three.js. Individual assets remain independently usable. Other engine compatibility remains a separate claim until tested.
5. Source/material provenance and the intended CC0 distribution records are complete, and reference images/prompts accompany the separate production archive. Runtime downloads do not claim to contain editable sources.
6. The run archive and a concise findings report identify what improved Kiln, what remains unresolved, and which workflows should carry into the next pack. Any shared changes receive their appropriate regression and packaged-workflow checks before final qualification.
